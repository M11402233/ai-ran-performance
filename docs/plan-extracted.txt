SIDE PROJECT  /  RESEARCH PROPOSAL
AI–RAN Performance Interferenceand Resource Optimizationon Commodity Hardware
基於一般消費級電腦之 AI 與 5G RAN 效能干擾分析及資源最佳化
Research focus   5G DU  ·  Linux perf  ·  Hardware counters  ·  Latency profiling  ·  CPU isolation
計畫型態  個人可重現實驗型 side project（不以論文發表為必要條件）
版本  v1.0     制訂日期  2026-10-30     預估時程  8 週（依硬體驗證與課業彈性調整）
摘要
本計畫以一台既有 Windows x86 電腦為起點，部署 Linux 上的 OCUDU（srsRAN Project 後繼專案）軟體化 5G gNB/DU，利用 ru_dummy 與 testmode 建立可控的 DU 計算負載。研究依序測量 AI / CPU 背景工作造成的干擾、利用 Linux perf 與 DU executor metrics 診斷原因，再驗證 CPU affinity、cgroup 隔離與 AI 工作負載限制是否改善即時處理表現。
所有核心結論限定在「單機、合成 DU 負載、指定軟硬體配置」條件。除非另行建置 UE / Core / radio emulator 的端到端路徑，否則不宣稱已量測真實 UE user-plane throughput，也不以平均值或最大值代替 P99。

1. 研究背景、文獻與研究定位
軟體化 RAN 將 MAC / PHY 等時間敏感運算帶到通用 CPU。既有文獻指出處理器層級行為和 RAN 效能值得共同觀察；另外 AI 與 RAN 共用資源可能造成吞吐量與錯誤率的變化，DRL 資源分配的收益也需要與自身系統開銷一起衡量。[R1–R3]
公開研究
已做的事
本專題的切入點
PRO-RAN (2026) [R1]
以 OCUDU / VTune 分析 CU/DU 的 CPU 與微架構特徵。
聚焦「AI 工作共置後」的 DU executor latency，採更低成本的 Linux perf 與小規模干擾實驗。
Jeong et al. (2025) [R2]
在 simulator / dataset 上評估 DRL CPU allocation。
先檢查真實 host 的控制成本、排程競爭與隔離效果，DRL 留作延伸。
Jung et al. (2026) [R3]
AI-and-RAN co-location 測試顯示受限條件下 DL 吞吐量降低、BLER 上升。
在 4-core 級消費設備測最小化測試案例與 CPU-side contention path。

研究定位：本案是 exploration + performance characterization + optimization validation；不宣稱首次提出 AI-RAN co-location 或 CPU pinning，重視可重現性、效能歸因與負結果的可解釋性。
2. 三個 Research Questions、假說與可測量條件
RQ1｜Performance interference：AI 工作會干擾 DU 嗎？
RQ1 — To what extent do concurrent AI training/inference and background CPU workloads alter DU task execution latency and queueing behavior on a commodity host?
假說 H1：在固定 DU workload 下，當 AI 的 CPU-side 活動或純 CPU 壓力增加時，DU executor 的 enqueue latency 或 task duration 可能惡化；效果大小取決於 CPU 共用程度。
自變項：背景工作 {none, CPU stress, GPU inference, GPU training}；每種低/高負載；DU testmode 配置固定。依變項：enqueue_avg / enqueue_max、task_avg / task_max、CPU usage、context switches、defers。必要對照：DU only。
通過判準：取得每一條件至少 5 次可重現的 runs；能報告效應方向、變異及不確定性。未發現干擾也算有效結果。
RQ2｜Bottleneck diagnosis：CPU 到底卡在哪裡？
RQ2 — Are observed DU degradations better explained by CPU scheduling interference, compute saturation, or measurable cache/memory-side changes?
假說 H2：部分惡化可由 context switches / CPU migrations / enqueue delay 的增長解釋；其他情況可能反映 cycles、IPC 或 cache behavior 的變化。這是待檢驗的競爭假說，不預先指定單一原因。
證據鏈：perf stat（cycles、instructions、cache references/misses、context switches）、perf record（hotspots）、DU metrics（executor latency / defers）、CPU affinity & frequency / thermal logs。PMU 計數需確認 CPU 支援；cache-misses 不能直接等於 DRAM bandwidth。
通過判準：至少分析 1 個發生變化或未發生變化的 scenario，提出兩種以上候選機制並用控制實驗排除混淆。
RQ3｜Resource optimization：隔離值得嗎？
RQ3 — Can CPU affinity, cgroup CPU limits, or AI-side concurrency throttling mitigate DU performance degradation without excessive loss of AI throughput?
假說 H3：在存在可測干擾的條件下，合理的 CPU core 配置或降低 AI CPU worker 數，可能縮短 DU enqueue delay；但 4-core 系統也可能因可用核心不足而產生反效果。
策略：A default；B CPU affinity（DU 與 AI 分核，按實際 logical/physical topology 安排）；C cgroup 限額或 cpuset；D PyTorch CPU threads/DataLoader workers 降低。比較：DU delay、AI samples/s（或 inference/s）、整體 CPU 使用、執行失敗率。
通過判準：提供相同 RQ1 條件下 before/after 的配對比較，說清楚改善幅度和 AI 端代價。DRL 控制器不是三個 RQ 的必要條件，列為獨立 stretch goal。

操作與混淆因子控制
固定 OCUDU git commit/tag、Linux kernel、BIOS/電源模式、CPU governor、AI seed、thread count、DU config；每次重啟需重新確認。
記錄 CPU 溫度與頻率；避免背景更新、瀏覽器、Windows host VM 爭用；若是筆電，固定接電與散熱條件。
測量工序需固定：先 DU warm-up，再開始背景工作與同步採樣；不同 run 使用明確 run_id、起止時間。
不要同時開啟多個重型 profiler 導致 instrumentation overhead 混淆；先獨立 perf stat，再選代表性情況 perf record。
cgroup v2、taskset 與 OCUDU 自身 thread affinity 可能互相作用；需驗證實際 CPU mask，不要假定 taskset 一定覆寫所有 worker。
6. 指標定義、資料處理與分析方法
指標
計算 / 取得方式
解讀注意事項
CPU utilization
OCUDU app_resource_usage、pidstat
不等於完成工作量；多核心 process usage 可超過 100%。
IPC
instructions / cycles
跨 CPU/負載比較時需說明頻率、event multiplexing 與 CPU 型號。
Cache MPKI
cache-misses / instructions × 1000
event 意義依 PMU 而異，非 DRAM BW 直接測量。
Enqueue latency
executor enqueue_avg / enqueue_max
平均與區間最大，不是 P99。
Task duration
executor task_avg / task_max
要取得 P95/P99 需每次 task tracing 或額外 instrumentation。
Context switches
perf / executor metrics
搭配排程追蹤解讀，不可直接證明 root cause。
AI progress
training steps/s、inference/s
評估優化對 AI 任務的代價。
Deadline misses
僅有明確 deadline 且可取得事件時
不得以 task_max > 某隨意門檻代稱標準化 deadline。

主圖 1：executor enqueue_avg / max vs. workload type。主圖 2：cycles、IPC、context switches 與 DU delay 的成對變化。主圖 3：Default / affinity / throttling 的 DU delay 與 AI throughput trade-off。
統計：每組至少 5 次獨立 runs；報告 median、mean、SD、95% CI（bootstrap 可選）、配對差值與 effect size。先畫所有原始點，避免只畫漂亮的 bar chart。若未取得逐任務時間戳，正式結果只使用 mean/max，不宣稱 P99。
預期影響沒有預設方向；若干擾差異接近零，應回報該 workload 在本硬體的 CPU-side activity、測量解析度與不確定性，不應盲目加大負載直到出現想要的現象。

9. 可選延伸：DRL 與真正的 RAN throughput
Extension A（資源管理 DRL）：在完成三個 RQ 後，先用離線記錄資料建立 toy environment：state = DU enqueue delay、CPU load、AI progress；action = AI CPU thread budget / training intensity；reward = DU latency penalty + AI progress。先比較 static 與 threshold rule，確保 DRL 超越簡單 heuristics 才有意義。不要把對 simulator 的改善宣稱為已證明的實機 RAN 最佳化。
Extension B（端到端傳輸）：若未來取得更強硬體與實作時間，再建立 UE emulator + Open5GS + ZeroMQ 等完整 user plane，測 iperf3 throughput、packet loss、RTT 等，並檢查與 dummy DU latency 的相關性。此路徑明顯超出本 MVP 的最低交付範圍。
